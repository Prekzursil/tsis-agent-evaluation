## 3. Custom-domain failure analysis (research value: where exactly does the agent fail against real store rules?)

`glm-5.3` agent vs `glm-5.3-flash` user, 56/56 units of `ecommerce2`. 42/56 units pass. All 14 failing units were autopsied (`analyze_failures.py`, output `results/failures_custom.json`):

**Per rule family (successes/units):** coupon 10/12 · vat 11/12 · return 8/12 · shipping 9/12 · cancel 0/4 · lost 4/4.

**Finding 1 — zero wrong write actions.** Across all 56 units the agent took **no** incorrect write against the store rules: 0 failed write-action checks, and the DB end-state matched the expected hash in 13 of the 14 failing units. The only DB mismatch in the whole domain (coupon_task_2, trial 1) is not an invalid-coupon application: after the agent correctly refused the expired SAVE20 (min-value reason), the *user simulator* asked to cancel the order so it could place a bigger one, and the agent complied with that explicit request — a user-simulator drift the task's gold DB does not model (`results/ecommerce2/results.json`, trial 1 trajectory: refuse → cancel → "once you place your new order over 100 EUR … I'd be happy to apply SAVE20").

**Finding 2 — every other failure is a COMMUNICATE-substring miss, not a rule violation.** The harness's `CommunicateEvaluator` is a literal substring matcher (`repo/src/tau2/evaluator/evaluator_communicate.py:69-71` — `info_str.lower() in message.content.lower().replace(",", "")`; the code even carries a `TODO: This could be improved!`). All 13 remaining failing units did the right thing (DB ✓, all action checks ✓) and *semantically* communicated the required fact, but never produced the exact required substring:

| Task (fails) | Required substring | What the agent actually said (verbatim, last message) |
|---|---|---|
| cancel_task_1 (4/4) | `confirmation email` | "You'll receive a cancellation **confirmation by email** shortly" — every trial |
| return_task_2 (4/4) | `outside` | declines the 50-day return, cites the "30-day window … firm policy", never the word "outside" |
| shipping_task_1 (2/4) | `updated` | address changed (DB ✓), new address recited, "Nothing else on the order has changed" |
| shipping_task_3 (1/4) | `unable` | "I'm sorry I **can't** redirect it for you" |
| vat_task_2 (1/4) | `200.00` | re-issued FR invoice correctly (DB ✓: net 200.00/VAT 40.00) but tells the customer only the unchanged total "240,00 €" in French formatting |
| coupon_task_2 (1/4, t0) | `expired` | declines correctly (DB ✓), explains minimum + "Expires: 30 September 2026 (**still valid**)" — see Finding 3 |

**Finding 3 — a task-authoring bug surfaced by the failure analysis.** coupon_task_2's gold communicate check demands the literal word "expired", but nothing in the domain gives the agent *today's date* (the policy and system prompt carry no current-date anchor; `tools.py` enforces expiry server-side via `date.today()`). The agent therefore read `expires_on: 2026-09-30` and honestly called it "still valid" (today is 2026-10-19), declining on the minimum-value rule instead. Authoring lesson recorded for v2: anchor "today" in the policy (as the shipped retail domain does), or require communicate strings the agent can derive from data it sees.

**Failure-mode taxonomy for the custom domain (56 units):** 13 substring-communication artifacts (23%) · 1 user-simulator-drift DB mismatch (2%) · 0 wrong write actions · 0 wrong declines. I.e. against *real store rules* the agent's action policy is effectively perfect in this domain; its measured pass^4 of 0.5714 is dominated by the harness's literal-substring communicate checks, not by rule violations.

**Prior custom domain `ecommerce_poc` (13 tasks, dual-control: user has its own write tools in-app)** — 3 failing units, a genuinely different failure mode: `ecomm_shipping_001` t2 and `ecomm_vat_002` t0/t1 fail because the agent never guides the *user* to perform the user-side write (`update_saved_address`, `update_saved_vat_id` via the user's discoverable tools) — the τ²-bench dual-control signature failure (agent does its half, user's half never happens → DB mismatch). One `ecomm_vat_002` trial additionally misses the read steps (`find_user_by_email`, `get_order_details`).
